## 1. GTM Philosophy

### 1-A. 市場投入思想の定義

IPPO の GTM は「プッシュ型」ではなく「引力型」である。

```
プッシュ型 GTM（IPPO が採用しない）:
  広告で認知 → セールスでクロージング → 契約 → 導入
  → ユーザーは「買わされた」と感じる
  → Founder の時間と金がなくなる
  → 辞める理由が「コスト」になりやすい

引力型 GTM（IPPO が採用する）:
  信頼で認知 → プロダクトが価値を証明 → ユーザーが自ら選ぶ
  → ユーザーは「自分で見つけた」と感じる
  → Founder の時間は「良いプロダクトを作ること」に使われる
  → 辞める理由が「価値がなくなった時だけ」になる
```

### 1-B. IPPO が選ばれる理由（3 層構造）

#### 層 1: 機能的理由（誰でも言える）

```
「記録が続く設計になっている」
「AI が自分のパターンを教えてくれる」
「月経・痛み・感情・睡眠が一元管理できる」
```

#### 層 2: 感情的理由（競合には言えない）

```
「私の症状が、データとして意味を持つ」
「同じ疾患の人が 500 人いることがわかって、孤独じゃなくなった」
「先生に説明するのに、このグラフを見せたら一度で伝わった」
```

#### 層 3: 社会的理由（10 年たって初めて言える）

```
「IPPOのデータが、子宮内膜症の治療ガイドラインを変えた」
「私が 5 年間記録したデータが、論文に使われた」
「日本の女性疾患の研究が世界水準になったのは、IPPO があったから」
```

**GTM の仕事は、ユーザーが「層 1」から「層 3」に移行する旅を設計することである。**

### 1-C. 10 年間変わらない競争優位

```
競争優位 1: 縦断の長さ（Longitudinal Depth）
  「2026年から記録したデータ」は 2036年に「10年分の縦断データ」になる。
  どの競合も、今日からでは追いつけない。時間だけが作れる資産。

競争優位 2: Consent の清潔さ（Consent Purity）
  BD-002（Consent Immutability）により、IPPO の Consent 記録は改ざん不可能。
  「このデータは完全な同意のもとで収集された」という証明が、
  Research Dataset の最大の価値になる。

競争優位 3: 疾患特化の深さ（Disease Specificity）
  Flo / Clue は月経追跡が核心。IPPO は「疾患を持つ女性の病態理解」が核心。
  疾患特化のデータ深度は、汎用ヘルスアプリが追い付けない専門性になる。

競争優位 4: 研究品質の信頼（Research Quality Trust）
  医師アドバイザー監修 + IRB 承認 + k-anonymity k≥5 + Consent Immutable の組み合わせ。
  これを全部満たす民間データプロバイダーは、世界的に見ても極めて稀である。
```

## 2. Ideal Customer Profile

### 2-A. ICP の定義原則

```
IPPOのICP選定基準:
  1. 記録動機が強い（症状の変動が激しく、追跡したい動機がある）
  2. 疾患の理解に困っている（既存の医療情報だけでは不十分と感じている）
  3. 長期記録が期待できる（慢性疾患 / 繰り返す症状）
  4. コミュニティが存在する（患者会・SNS・フォーラム経由でリーチできる）
  5. 研究ニーズが高い（疾患の研究データが希少で、研究機関が欲しがっている）

これらすべてに高得点が入る疾患から優先する。
```

### 2-B. ICP 優先順位（完全版）

#### Tier 1（今すぐ始める / 最優先）

**子宮内膜症（Endometriosis）**

```
記録動機: ★★★★★（月経痛・腹痛が毎月変動する）
理解困難度: ★★★★★（診断に平均 7〜12 年かかる）
長期記録: ★★★★★（慢性疾患 / 治癒しない）
コミュニティ: ★★★★☆（Twitter / note / 患者会が活発）
研究ニーズ: ★★★★★（有病率 10% / 研究データが圧倒的に不足）
→ 総合スコア: 24/25 — 最優先ターゲット

日本の市場規模: 推定 200〜300 万人
特性: 20〜40 代、医療不満足度が高い、情報収集に熱心
獲得方法: 子宮内膜症 SEO / note 記事 / Twitter（X）エンドメ患者コミュニティ
```

**PCOS（多嚢胞性卵巣症候群）**

```
記録動機: ★★★★☆（月経不順・体重変動・ホルモン値が変動）
理解困難度: ★★★★★（症状が多様で、自分のタイプがわかりにくい）
長期記録: ★★★★★（慢性疾患）
コミュニティ: ★★★★☆（Twitter / note で活発）
研究ニーズ: ★★★★★（インスリン抵抗性 / ホルモン治療の研究データが不足）
→ 総合スコア: 22/25 — 並行最優先

日本の市場規模: 推定 100〜200 万人
特性: 20〜40 代、体重・食事・運動との関係を追跡したい
獲得方法: PCOS SEO / Twitter（X）PCOSコミュニティ / note 記事
```

#### Tier 2（Wave2 Phase B 以降 / 準最優先）

**PMS / PMDD**

```
記録動機: ★★★★★（月経前 2 週間の症状が毎月繰り返す）
理解困難度: ★★★★☆（症状の因果関係がわかりにくい）
長期記録: ★★★★☆（慢性的だが症状緩和で卒業することがある）
コミュニティ: ★★★☆☆（Twitter で増加傾向）

**子宮腺筋症（Adenomyosis）**

```
記録動機: ★★★★★（月経痛・過多月経が強烈）
理解困難度: ★★★★☆（子宮内膜症との鑑別が難しい）

コミュニティ: ★★★☆☆（認知度が低く、コミュニティが小さい）
研究ニーズ: ★★★★☆（子宮内膜症との共存が多い / データが少ない）

ICP備考: 子宮内膜症ユーザーとの重複が多いため、
          エンドメ ICP の延長として自然に流入する

#### Tier 3（Wave3 以降）

**更年期症状（Perimenopause / Menopause）**

## 4. User Journey

### 4-A. 理想フローの全体設計

```
Stage 0: 認知（Awareness）
  ─────────────────────────────────
  トリガー: 「子宮内膜症 記録 アプリ」「PCOS 症状 管理」の検索
             または、患者コミュニティでの言及 / note 記事
  Founder の行動: SEO 記事を書く / コミュニティで自然に存在感を示す
  期間: 2026年〜（今すぐ開始 / Wave2 完了を待たない）

Stage 1: 登録（Registration）
  ─────────────────────────────────
  場所: App Store / LP
  摩擦の最小化: 「疾患を選ぶだけで始められる」
  第一印象: 「これは自分のためのアプリだ」と感じさせる
  目標: インストール → 初回記録 まで 5 分以内

Stage 2: 最初の記録（First Record）
  ─────────────────────────────────
  最も重要なステップ: 「最初の記録」が習慣化の分岐点
  設計: 記録直後に「記録しました」の即時フィードバック
         + 「3日分たまると、最初のサマリーが見られます」の予告
  目標: 登録日から 7 日以内に 3 回以上記録する

Stage 3: パターン発見（Pattern Discovery）
  ─────────────────────────────────
  タイミング: 30 日後
  イベント: 「30日サマリー」の自動生成（Free でも閲覧可能）
  設計: 「月経前に痛みスコアが上昇する傾向があります」等の
         事実ベースのサマリーを表示する
  目標: 「これは使える」と感じさせる / 継続動機の強化

Stage 4: 継続（Retention）
  ─────────────────────────────────
  目標: 30日継続率 ≥ 60% / 90日継続率 ≥ 40%
  設計:
    → 記録が途切れたら「3日空いています」の穏やかな通知
    → 「7日連続記録」「30日記録」のマイルストーン可視化
    → 月次の「あなたの今月の記録サマリー」（Free）

Stage 5: Premium 転換（Conversion）
  ─────────────────────────────────
  タイミング: 30〜90 日の記録が蓄積した後
  トリガー: 「Signal Insight（詳細分析）を見るには Premium が必要です」
  設計:
    → Free では「傾向があります」止まり
    → Premium では「黄体期の痛みスコア平均が 6.2 で、卵胞期（3.1）の 2 倍」等の詳細
    → 「先生に見せたいグラフ」が Premium に配置される
  目標: 30 日以上記録したユーザーの Premium 転換率 ≥ 8%

Stage 6: Research Consent（社会的関与）
  ─────────────────────────────────
  タイミング: 登録から 90 日後に表示
  設計: 「あなたの 3 ヶ月分の記録は、女性疾患の研究に使える貴重なデータです。
         匿名化処理（k≥5）を行った上で、学術研究に提供しますか？」
  オプトイン前提。強制しない。しかし「意義」を伝える。
  目標: Research Consent 同意率 ≥ 50%（長期継続ユーザーで高くなる）

Stage 7: 長期利用・伝道者（Advocacy）
  ─────────────────────────────────
  タイミング: 12 ヶ月以上の継続
  イベント: 「1年記録達成」の特別メッセージ
             「あなたのデータが、研究に使われました」の通知（Wave3 以降）
  設計: 長期ユーザーが「IPPO を他の人に伝えたくなる」体験を作る
        → 「私の症状を友達に伝える」シェア機能（匿名化された自分のサマリー）
  目標: 12 ヶ月継続率 ≥ 40% / NPS ≥ 40
```

### 4-B. ユーザージャーニーとプロダクトの接続

```
認知 → 登録: LP / App Store の説明文 / SEO 記事 / コミュニティ口コミ

### 5-B. 各プランの価値提案（GTM 視点）

#### Free — 「記録して、自分の記録を自分で見る」

```
価値提案: 「まず記録してみる。無料でいつでも始められる。」

提供機能（GTM 観点での設計意図）:
  ✓ 疾患登録 + Signal 記録（6種）
  ✓ 月次サマリー（「先月の痛みの平均は 5.1 でした」等の事実提示）
  ✓ 記録の閲覧（カレンダー / タイムライン）
  ✓ データエクスポート（CSV / 医師に渡す用途）

提供しない（Premium の動機になるもの）:
  ✗ Signal Insight（詳細な傾向分析）
  ✗ Pattern Discovery（月経周期との相関分析）
  ✗ 類似症例の表示（Wave2 Phase D 以降）

GTM の意図:
  Free は「記録の習慣を作る場所」である。
  「詳しく知りたい」欲求を 30〜90 日かけて育て、Premium に誘う。
  Free で離脱するユーザーは、そもそも有料化しないユーザーである。
  離脱を防ぐより、記録を続けるユーザーを Premium に転換することを優先する。
```

#### Premium — 「自分のパターンを理解する」

```
価値提案: 「月 980 円で、自分の症状パターンが見えてくる。先生に見せられるグラフも作れる。」

追加機能（Free に加えて）:
  ✓ Signal Insight（AI ルールベース分析 / 週次・月次のパターン提示）
  ✓ Pattern Discovery（月経周期との相関 / 睡眠・感情との相関）
  ✓ 医師向けレポート生成（PDF / 診察時に見せる用）
  ✓ 通知カスタマイズ（症状悪化の傾向がある時期を事前に通知）

Premium の「先生に見せられるグラフ」は最強の継続動機である:
  → 「これを持って行ったら先生に伝わった」体験 = 解約できなくなる
```

#### Pro — 「自分を研究する人のためのプラン」

```
価値提案: 「月 1,980 円で、自分のデータを完全にコントロールできる。」

追加機能（Premium に加えて）:
  ✓ 完全なデータダウンロード（全履歴 / JSON / CSV）
  ✓ カスタム Signal 設定（独自の記録項目を追加）
  ✓ 類似症例の詳細表示（k≥5 の症例グループとの比較詳細）
  ✓ 月経周期の予測精度向上（Pro の記録密度が高い場合）

対象: 自分の疾患を徹底的に調べている人 / 治験参加経験者 / 医療従事者
```

### 5-C. 価格とユーザー心理の設計

```
価格設計の心理原則:

  Free → Premium の障壁を低くする:
    → ¥980/月 は「コーヒー 1 杯分」という表現が有効
    → 年払い（¥7,800）は「月換算 ¥650 / 1日あたり 21 円」

  Premium → Pro への自然な移行を設計する:
    → Pro の「カスタム Signal」は「食事記録」「薬記録」等を独自に追加できる
    → 「自分の疾患を本気で管理している人」が自然に Pro に移行する

  Research License の「安心感」を強調する:
    → 「IRB 承認があれば申し込める」「特定の研究テーマは割引」
    → 「申し込みはメールだけ / 電話営業は一切なし」を明記する
```

## 8. Research Customer Journey

### 8-A. Research 顧客の購買サイクル

```
IPPO の Research Dataset の「顧客」は誰か:
  顧客 A: 大学・研究機関（学術 / L1 Academic License ¥350K〜¥700K / 年）
  顧客 B: 製薬企業（商業研究 / L2 Commercial License ¥3M〜¥10M / 年）
  顧客 C: 政府・公的研究機関（政策研究 / L3 Government License ¥1M〜¥5M / 年）

Research 顧客の購買サイクルは「SaaS の購買」とは全く異なる:
  → 意思決定者が「研究者個人」ではなく「研究機関」である
  → 購買には IRB 承認 + 機関承認 + 予算申請 が必要（3〜12ヶ月）
  → 一度契約すると「更新型」になりやすい（研究が継続するため）
  → 営業は「存在を知ってもらうこと」が 9 割 / 残りは「手続き補助」
```

### 8-B. Research Customer Journey 設計

```
Step 1: 認知（Awareness）— 研究者がIPPOを知る
  チャネル:
    → 医師アドバイザーが学会・研究会で言及する（最有力）
    → 患者コミュニティで「IPPO にデータを提供している」という話が広まる
    → IPPO Dataset を使った論文が PubMed / J-STAGE に掲載される（Wave3 以降最有力）
    → Founder の note / Twitter で「Research Dataset の提供方針」を発信する
  Founder の工数: 0〜2 時間/月（コンテンツの一部として含める）

Step 2: 関心（Interest）— 研究者が IPPO のデータを調べる
  チャネル:
    → IPPO LP の「研究者向け情報」ページを参照する
    → メールで「Research Dataset の概要を教えてほしい」と連絡してくる
  Founder の対応:
    → 「Research Dataset 概要資料」（PDF 2 ページ）を作成しておく（初回のみ 4〜6 時間）
    → 問い合わせには「翌営業日以内」に返信する
    → 電話・ビデオ MTG は必要に応じて 1 回（30〜60 分）

Step 3: 評価（Evaluation）— 研究者が IRB 申請・機関承認を進める
  IPPO の役割:
    → IRB 申請書のデータセクションに必要な情報を提供する（k-anonymity 仕様 / 変数定義等）
    → 「IRB 申請サポートパッケージ」（雛形 / 変数定義書）を用意しておく
  Founder の工数: 1〜2 時間/件（資料提供 + Q&A）

Step 4: 契約（Contract）
  プロセス:
    → 契約書雛形（BDS-002 / Section 3-D の必須条項含む）を送付する
    → IRB 承認証明書の受領を確認する（BD-046 必須）
    → 電子署名（DocuSign 等）で完結する（対面不要）
  Founder の工数: 2〜3 時間/件（契約書確認 + 受領確認）

Step 5: 提供（Delivery）
  プロセス:
    → Dataset の生成（BD-021 の Founder Gate / Founder が手動で確認）
    → Supabase から安全な方法で提供（暗号化 ZIP / セキュア転送）
    → 「Dataset 説明書」（変数定義 / k-anonymity 処理の説明）を同梱
  Founder の工数: 4〜8 時間/件（Dataset 生成 + 確認 + 提供）

Step 6: 更新（Renewal）
  設計:
    → 年次更新。「継続するには IRB 更新証明を提出してください」の自動リマインド
    → 更新率を高めるために「新規追加データ（昨年比 X 件増）」のレポートを送付
  Founder の工数: 1〜2 時間/件（更新確認 + 最新 Dataset 提供）
```

### 8-C. Research 収益が「自然に」成長する仕組み

```
論文の引用が次の顧客を連れてくる:
  「IPPO Dataset を使った研究」が論文になる
  → 論文を読んだ別の研究者が「このデータを使いたい」と来る
  → Founder は何もしなくても、研究者が来る

この「引用の連鎖」が Research 収益の最大の成長エンジンである。
したがって、最初の論文を早く出すことが最重要戦略である。

最初の論文への道:
  2027年: 医師アドバイザー招聘 → 研究機関との接続
  2028年: 最初の Research License 契約
  2029年: 最初の学術論文（IPPO Dataset 使用）が発表される
  2030年以降: 論文引用が累積 → 自然な問い合わせが増加
```

## 9. B2B Strategy

### 9-A. B2B の設計原則

```
IPPO の B2B は「Founder が売る B2B」ではない。
「ユーザーが使っていて、医療機関が導入したくなる B2B」である。

B2B 成立の条件:
  「IPPO を使っているユーザーの記録を、診療に活用したい」という医師が
  自然に現れる状況を作ることが先決。

この状況は以下で生まれる:
  → ユーザーが「IPPO の先生向けレポートを持って受診した」
  → 医師が「このアプリのデータは使いやすい」と感じた
  → 医師が「クリニック全体で導入したい」と考えた
  → Clinic API の問い合わせが来る

Founder は「待つ」設計をする。ただし「LP で Clinic API の存在を知らせる」ことは行う。
```

### 9-B. Clinic API の設計（Wave4 / 2031年〜）

```
Clinic API が提供する価値:
  医師側: 「患者の IPPO 記録に診療システムからアクセスできる」
          「患者の許可のもとで、過去 6 ヶ月の症状推移を確認できる」
  患者側: 「かかりつけ医が IPPO を使っていると、記録が活かされる」
  IPPO 側: ¥30K〜¥150K/月 の安定収益

導入フロー（営業なし）:
  → LP に「医療機関向け API」のページを設置
  → 「問い合わせフォーム」から申し込み
  → Founder が 1 件ずつ確認 + 契約書送付（電子署名）
  → API キー発行 + 技術ドキュメント提供（自己解決型）

対象クリニック:
  → 婦人科専門クリニック（子宮内膜症 / PCOS 専門）
  → 不妊治療クリニック
  → 女性向け健康管理クリニック

パイロット設計（Wave3 終了後 / 3 クリニック）:
  → 医師アドバイザー経由で最初の 3 クリニックを紹介してもらう
  → 無償 or 割引期間（3ヶ月）でパイロット → フィードバック収集 → 正式版
  → Founder の工数: 月 4〜6 時間（3 クリニック分）

拡大方針:
  → パイロット成功後、「Case Study」を LP に掲載する
  → 「このクリニックが使っている」が、次のクリニックを引き寄せる
  → 目標: Wave4 完了時に 10〜20 クリニック（Founder 一人で管理可能な上限）
```

### 9-C. B2B の Founder 運営上限

```
Founder 一人で維持できる B2B 規模の上限:

  Research License 顧客: 10〜15 件/年（月 4〜6 時間）
  Clinic API 顧客: 20〜30 クリニック（月 4〜8 時間 / 技術問い合わせ対応含む）
  合計 B2B 負荷: 週 2〜4 時間（BBS-005 週 45 時間の範囲内）

この上限を超える場合は「自動化 or 待機リスト」で対応する。
「キャパオーバーで断る」は問題ではなく「高品質維持の証明」である。
```

### 12-B. Founder が「やらない」GTM 活動

```

  × 展示会出展（準備含め 40〜80 時間 / 回 の浪費）

  × SNS のフォロワー数を増やすためだけの発信（中身のないポストをしない）
  × ビジネスコンテスト参加（時間対効果が低い / VC を引き寄せる副作用）
  × アフィリエイト / インフルエンサーマーケティング（広告に準じるため禁止）
```

## 13. リスク

### GTM リスク（他文書と重複しないもの）

#### R-GTM-01: ユーザー獲得が予測より遅い

```
深刻度: MEDIUM
シナリオ: SEO / コミュニティ経由の流入が想定より 50% 少ない
           Wave2 Phase D（Signal Insight）完了時点でも有料ユーザーが 100 名未満
影響: MRR が目標の 50% 以下 / Founder のモチベーション低下
軽減: 「記録を続けるユーザーの質」を最優先とし、量を追わない設計にする
      → 100 名でも「3年以上記録するユーザー」が 50 名いれば Research Dataset の価値は生まれる
      → Founder は「ユーザー数」ではなく「記録継続率」を見る
残存リスク: 低（目標の設計自体を「量より質」にしているため）
```

#### R-GTM-02: Premium 転換率が想定より低い

```
深刻度: MEDIUM
シナリオ: 30 日以上記録したユーザーの Premium 転換率が ≤3%（目標 8%）
影響: MRR が目標の 37% / 事業収益が Founder の生活費を下回る可能性
軽減:
  → Signal Insight の「价値体験」を強化する（Free でも「少しだけ見える」設計）
  → 「先生に見せたいグラフ」のモック / プレビューを Free ユーザーに見せる
  → ¥980/月 が高すぎると感じる場合、学生向け割引（¥490）を検討する
残存リスク: 中（プロダクト価値に大きく依存するため）
```

#### R-GTM-03: Research 収益が Wave3 まで待てない

```
深刻度: LOW
シナリオ: Wave2 期間の MRR が低く、Founder の財務に余裕がなくなる
影響: Founder がアルバイト等で時間を使う → Wave2 の完了が遅れる → 悪循環
軽減:
  → Founder は「Wave2 完了までの 2 年間」の生活費の確保を事前に確認する
  → 必要に応じて Pro プランの早期リリース（¥1,980 × 少数の熱心なユーザー）
  → Research License の「早期予約価格」制度を医師アドバイザー経由で告知
残存リスク: 低（IPPO の財務設計が「低コスト運営」前提のため）
```

#### R-GTM-04: 医師アドバイザーが見つからない

```
深刻度: HIGH
シナリオ: Wave2 Phase D 前に適切な医師アドバイザーが見つからない
