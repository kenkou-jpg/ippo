## Executive Summary

### Council の総意

IPPO は女性疾患の縦断データを扱うプラットフォームである。
扱うデータの性質上、以下の 4 つの規制領域が同時に適用される:

```
① 個人情報保護法（要配慮個人情報 / 匿名加工情報 / 研究例外）
② 薬機法・医療機器規制（SaMD / プログラム医療機器）
③ 臨床研究法・人を対象とする医学系研究倫理指針（IRB）
④ 海外データ保護規制（台湾個人資料保護法 / 韓国 PIPA / 豪州 Privacy Act / GDPR）
```

これらすべてに対して「事前に方針を決めること」が
IPPO の 10 年運営を守る最も重要な行為である。

**Founder 一人運営でも遵守できる規制設計**を本文書は定める。
規制は「障壁」ではなく「IPPO の信頼の源泉」である。

### 総合評価

| 規制領域 | 現在の設計 | リスク水準 | 本文書での対処 |
|---|---|---|---|
| 個人情報保護法 | k-anonymity / Consent 設計あり | 中 | 方針を明文化・専門家確認を定める |
| SaMD 規制 | BD-031（診断禁止）あり | 高 | 安全ラインを明文化・法的見解取得を義務化 |
| IRB / 倫理審査 | BD-021（Founder 承認）あり | 中〜高 | 利用段階別の必要性を明文化 |
| Consent 設計 | BD-002（Immutable）あり | 低〜中 | 研究 Consent / AI Consent を追加設計 |
| 海外規制 | 未設計 | 展開時に高 | 国別対応方針を明文化 |

### 最終判定

```
CONDITIONAL GO

IPPOの規制・医療・倫理設計は「方向性として正しい」。
しかし以下の条件を満たすことで初めて「安全」になる:

  条件 1: Wave2 Phase D 着手前に法律専門家への SaMD 該当可否相談完了
  条件 2: Research Dataset 初回提供前に IRB 方針の法的確認完了
  条件 3: 医師アドバイザー 1 名の招聘（Wave2 Phase D 前）
  条件 4: Consent 設計の Research Consent / AI Consent 追加（Wave2 Phase D 前）
  条件 5: 台湾展開前に個人資料保護法への対応確認完了

これらを順守すれば、Founder 一人で 10 年間安全に運営できる。
```

## 1. 日本の法規制整理

### 1-A. 個人情報保護法における IPPO データの分類

#### 要配慮個人情報（最重要）

```
定義（個人情報保護法 第 2 条 3 項）:
  病歴、診療情報、健康診断の結果等は「要配慮個人情報」に該当する。

IPPOデータの該当性:
  ✓ 疾患名（子宮内膜症・PCOS 等）  → 要配慮個人情報（病歴）
  ✓ 症状記録（痛みスコア・月経記録）→ 要配慮個人情報（健康に関する情報）
  ✓ 実験記録（服薬・食事介入）      → 要配慮個人情報（診療に準ずる情報）
  △ 感情スコア（moodScore）         → 心身の状態に関する情報。要配慮に該当する可能性あり
  △ 睡眠スコア                      → 同上

適用される追加義務:
  → 取得には本人の「明示的な同意」が必要（黙示的同意は不可）
  → 第三者提供には個別の同意が必要（オプトアウト不可）
  → 安全管理措置の水準が一般個人情報より高い

現在の設計との整合性:
  BD-002（Consent Immutability）: 同意記録が Append-Only で永久保存 → ✓ 対応済み
  BD-021（Founder 承認）: Research Dataset の第三者提供に Founder 承認必須 → ✓ 対応済み

不足している可能性:
  → 「明示的な同意」が何をカバーするかの詳細設計が未文書化
  → 「要配慮個人情報を取得している」という利用規約・プライバシーポリシーへの明示
  → 安全管理措置（暗号化・アクセスログ等）の具体的水準の未文書化
```

**決定 R-JP-01:** Founder は法律専門家と協力して、IPPO のプライバシーポリシーに「要配慮個人情報の取得・利用」を明記し、取得の同意フロー（ユーザーが入力する前に「これは要配慮個人情報です」と明示する画面）を設計すること。これは Wave2 Phase A 完了前に実施する。

#### 匿名加工情報 vs 仮名加工情報

```
匿名加工情報（個人情報保護法 第 2 条 6 項）:
  「特定の個人を識別できない」かつ「個人情報を復元できない」情報。
  作成・利用・第三者提供に関する規制が緩和される（同意不要で提供可能）。

仮名加工情報（個人情報保護法 第 2 条 5 項）:
  「他の情報と照合しない限り特定の個人を識別できない」情報。
  第三者提供には原則として本人同意が必要（匿名加工情報より規制が強い）。

IPPOの k-anonymity 設計との関係:
  BD-021（k-anonymity k≥5）は「設計上の匿名化基準」であり、
  個人情報保護委員会が定める「匿名加工情報」の要件とは別概念である。

重要問題:
  IPPO の Research Dataset が法的に「匿名加工情報」の要件を満たすかどうかは
  個人情報保護委員会のガイドラインへの照合が必要。
  k-anonymity k≥5 だけでは法的「匿名加工情報」に該当しない可能性がある。

  「匿名加工情報」の法的要件（個人情報保護委員会規則）:
    1. 特定の個人を識別できる記述等の削除
    2. 個人識別符号の削除
    3. 不正アクセスによる取得防止
    4. 作成方法の開示義務
    5. 作成・利用の公表義務
    6. 識別行為の禁止

推奨アクション:
  法律専門家に「IPPOの k-anonymity 処理後の Research Dataset が
  匿名加工情報に該当するか」を確認する。
  仮名加工情報として扱う場合の規制も併せて確認する。
```

**決定 R-JP-02:** Research Dataset の提供前に、法律専門家への「匿名加工情報該当性確認」を必須とする。この確認なしに Research Dataset を外部研究機関に提供することを禁止する（BBS-002 を補強する規制上の根拠）。

#### 研究利用の例外規定

```
個人情報保護法 第 18 条 3 項 / 第 23 条 1 項の例外:
  学術研究機関が学術研究の用に供する場合、
  個人情報の目的外利用・第三者提供の制限が適用されないことがある。

IPPOへの適用可能性:
  IPPO 自体は「学術研究機関」ではない（民間事業者）。
  ただし、IPPO から大学・研究機関への Research Dataset 提供は、
  「学術研究に該当する場合の例外」として扱える可能性がある。

要件（個人情報保護委員会のガイドライン）:
  → 学術研究目的である必要がある
  → 目的の範囲内での利用である必要がある
  → 適切な安全管理措置が取られている必要がある

推奨:
  Research Dataset の提供先が「学術研究機関」か「学術研究目的」かを
  License 契約書に明記する（BBS-002 の L1 Academic License に追記する）。
  製薬企業への提供は「研究例外」の対象外であることを前提に設計する。
```

#### 保存期間・本人開示・削除請求

```
保存期間の方針:

  Layer 1（Record）/ Layer 2（NetworkSignal）:
    → 「ユーザーが利用する限り永久保存」を基本方針とする（BD-015 / BD-022 準拠）
    → アカウント削除時の扱い: GDPR 対応と個人情報保護法対応を統一設計する
    
  同意記録（consent_events）:
    → BD-002（Immutable / 永久保存）を維持する
    → 法的義務として「ユーザーの同意を証明できること」が必要
    
  ippo_events（Domain Events）:
    → BD-017（Immutable）を維持する
    → 保存期間の法的上限は現在不明。法律専門家に確認する。

本人開示請求（個人情報保護法 第 33 条）:
  → ユーザーが「自分の個人情報の開示」を請求できる
  → IPPO は「自分のデータのエクスポート」機能を有料プランに含める（BUSINESS_STRATEGY 準拠）
  → 請求への対応期限: 法律上「遅滞なく」（一般的には 2 週間以内）
  → 対応方法: アプリ内のエクスポート機能 or メール申請フォーム

削除請求（個人情報保護法 第 35 条 / GDPR 第 17 条）:
  → 個人情報保護法: 「本人申請による削除」の義務あり
  → IPPO の設計（BD-015 / BD-019）は「Hard Delete より匿名化優先」だが、
    法的には「削除できない理由の説明」または「削除」が必要。

  削除請求への IPPO 方針（決定）:
    → GDPR 対応方針（匿名化 or 物理削除）を個人情報保護法にも適用する
    → 「匿名化（pseudonymization）を行い、個人特定不可の状態にする」を
      「削除の代替措置」として利用規約に明記する
    → Consent 記録（consent_events）のみ「法的証拠として保存」を理由に
      完全削除せず、非個人化（userId を別 ID に置換）する設計を検討する
    → 実装判断は法律専門家の見解後に Founder が決定する（設計変更なし）

国外移転（Supabase 利用）:
  → IPPO は Supabase（米国発クラウド）を利用している
  → 個人情報保護法 第 24 条（改正後の第 28 条）:
    国外にある第三者への提供には、適切な安全管理措置 or 本人同意が必要
  → 対応: Supabase の利用が「国外移転」に該当するかを法律専門家に確認する
    （Supabase の日本リージョン利用 or 標準契約条項（SCC）の利用を検討）
```

**決定 R-JP-03:** IPPO のプライバシーポリシーには以下を明記する: (1) 要配慮個人情報の取得と利用目的、(2) Supabase（国外サーバー）へのデータ移転の事実、(3) 本人開示請求・削除請求の手順、(4) Research Dataset 利用の概要と同意の必要性。Wave2 Phase A 完了前に法律専門家によるレビューを受けること。

### 1-B. 研究利用に関する特別整理

```
「人を対象とする医学系研究に関する倫理指針」（文部科学省・厚生労働省・経済産業省）:
  IPPO の Research Dataset を用いた研究が「人を対象とする医学系研究」に
  該当する場合、倫理審査委員会（IRB 相当）の承認が必要になる。

IPPOのデータが「人を対象とする医学系研究」に該当するか:
  → 「人の健康に関するデータを収集・分析して、知識を得ること」は
    広く「人を対象とする研究」に含まれる可能性がある。
  → ただし、IPPO が研究を「実施」するのではなく、
    「研究者に Dataset を提供する」立場である場合、
    倫理指針の適用主体は Dataset を利用する「研究者側」になる。

IPPO の立場の整理（重要）:
  IPPO は「研究の実施主体」ではなく「データプロバイダー」として位置づける。
  この位置づけにより:
    → IRB の取得責任は「Dataset を利用する研究機関側」にある
    → IPPO の責務は「IRB 承認済みの研究にのみ Dataset を提供すること」

  この方針は BBS-002（Research Dataset 提供条件: IRB 承認必須）と整合する。
```

## 2. AI 規制整理（SaMD 問題）

### 2-A. SaMD（Software as a Medical Device）該当可能性

```
薬機法におけるプログラム医療機器（SaMD）の定義:
  「疾患の診断、治療、予防に使用することを目的とするソフトウェア」が
  プログラム医療機器（医療機器プログラム）として規制される。

  2021年薬機法改正以降、以下のカテゴリが明確化された:
    クラス I（リスク低）: 一般的な健康管理、生活習慣改善アプリ
    クラス II（リスク中）: 診断補助プログラム（医師の判断を支援するもの）
    クラス III（リスク高）: 独立した診断を行うプログラム

IPPOの各機能のSaMD 該当可能性評価:

  Signal Insight「あなたの痛みスコアは先週比 +1.4 上昇しています」
    → 疾患の診断・治療に使用する目的はない → クラス I 以下 → 低リスク
    → ただし「悪化を示唆するサイン」等の表現を使えばクラス II 可能性

  Pattern Discovery「黄体期に症状が集中するパターンがあります」
    → 「疾患のパターン提示」は診断に近い表現になりうる → 要注意
    → 「医療アドバイスではありません」の免責だけでは不十分な可能性

  Case Recommendation「あなたと類似した症例が 12 件ありました」
    → 「治療方針の選択に影響を与える」設計ならクラス II の可能性
    → 「参考情報の提示のみ」ならクラス I 以下

  Disease Cluster「あなたの症状強度は同疾患グループの上位 5%」
    → 「自分の病態を他者と比較する」機能。治療判断には繋がらない
    → クラス I 以下の可能性が高い

  AI Signal Insight（Wave2 / ルールベース）
    → LLM を使わない統計テンプレートベースなら低リスク
    → 文言に「〜の可能性があります」「医師に相談してください」が入ると要注意

安全ライン（絶対に超えてはいけない表現）:
  × 「あなたの症状から〇〇病が疑われます」（診断示唆）
  × 「この数値は危険なレベルです。今すぐ病院に行ってください」（緊急度判定）
  × 「このサプリメントが効果的です」（治療指示）
  × 「先週のスコアは悪化しています。悪化の原因として〇〇が考えられます」（因果断定 + 示唆）

安全な表現例:
  ✓ 「先週の痛みスコアの平均は 6.2 で、3週間前（4.8）より 1.4 高い記録です」（事実の提示）
  ✓ 「黄体期に記録した症状の回数が多い傾向が確認されました」（パターンの提示）
  ✓ 「記録されたデータのサマリーです。症状の変化は担当医師にご相談ください」（フッター）
```

**決定 R-AI-01（BD-031 の強化版）:** AI 出力の安全ラインを以下の 3 段階で定義する。

| レベル | 定義 | 対応 |
|---|---|---|
| SAFE | 事実の数値提示のみ | 自動公開可 |
| CAUTION | パターン提示（診断を含まない）| AISafetyValidator 必須 + 免責表示必須 |
| PROHIBITED | 診断・治療指示・緊急度判定・因果断定 | 設計上出力不可（BD-031 絶対禁止）|

### 2-B. SaMD 法的確認の手順

```
Wave2 Phase D 着手前に必須の行動:

  Step 1: 独立行政法人 医薬品医療機器総合機構（PMDA）のガイダンス確認
    → 「プログラムの医療機器該当性に関するガイダンス」（2023年版）の精読
    → 無料で入手可能 / Founder が自ら読む（1〜2 時間）

  Step 2: 薬事専門弁護士 or 薬事コンサルへのスポット相談
    → IPPO の AI 機能仕様書（Signal Insight / Pattern Discovery の出力例）を持参
    → 「SaMD に該当するか / 該当するならクラスは何か」の法的見解取得
    → 費用目安: 5〜15 万円（スポット相談 / 2〜4 時間）

  Step 3: 見解に基づく対応
    → クラス I 以下: 「医療機器ではない」旨をプライバシーポリシー / LP に明記
    → クラス II 以上: 承認申請の検討 or 機能設計の変更（当該機能の削除 or 文言修正）

  Founder へのアドバイス:
    「Signal Insight の出力が SaMD に該当しない」という確信なしに
    Phase D を開始してはならない。
    Phase D 完了後に「SaMD 該当」が判明した場合、
    機能の全面撤回 or 薬事承認取得（2〜3 年 / 数千万円）が必要になる。
    これは Founder 一人運営を致命的に破壊するリスクである。
```

**決定 R-AI-02:** Wave2 Phase D（PR-057: Signal Insight Service）の着手前に、薬事専門弁護士または薬事コンサルによる「SaMD 該当可否の書面見解」を取得することを必須とする。この確認が完了するまで PR-057 の着手を Founder が宣言的に禁止する。

### 2-C. AI Safety Layer の設計方針（BD-031 / BD-038 を補強）

```
Wave2 AI Safety Layer（PR-062）で守るべきこと:

  必須チェック項目（自動テストで実行）:
    1. 診断的断定の検出
       禁止パターン: 「〜病です」「〜が疑われます」「〜の症状です」
    
    2. 治療指示の検出
       禁止パターン: 「〜してください」「〜を飲んでください」「〜をやめてください」
    
    3. 緊急度判定の検出
       禁止パターン: 「すぐに病院に」「緊急」「危険」「重篤」
    
    4. 因果断定の検出
       禁止パターン: 「〜が原因です」「〜のせいで」「〜が引き起こしています」
    
    5. 免責表示の存在確認
       必須: 「これは医療アドバイスではありません」or 同等の免責文言

  免責文言の標準テンプレート（日本語）:
    「このサマリーはあなたの記録データに基づく情報提示です。
     医療診断や治療指示ではありません。
     症状や体調の変化については、担当の医師にご相談ください。」

  追加すべき免責（現設計に不足）:
    → 「IPPOは医療機器ではありません」の明示
    → AI 出力への「AI が生成したサマリーです」のラベル
    → 「個人差があります / すべての人に当てはまるわけではありません」

  AI Safety Layer の運用ルール:
    → 禁止ワードリストは医師アドバイザーが半年ごとにレビューする
    → 新しい禁止パターンの発見時は即時リストに追加し、Founder が承認する
    → 禁止ワードリストは公開ドキュメントとして管理する（透明性）
```

## 3. Clinical Research 方針

### 3-A. IPPO の Research における立場の明確化

```
IPPO の研究における立場:
  IPPO は「研究の実施主体」ではない。
  IPPO は「研究データの管理者・提供者」である。

この区別が重要な理由:
  → 「実施主体」であれば IRB 承認の取得義務が IPPO に生じる
  → 「提供者」であれば IRB 承認取得義務は研究利用者側にある
  → IPPO は「提供条件として IRB 承認を求める」立場を取る

IPPO が「実施主体」にならないための設計:
  → IPPO は研究の仮説設定・研究計画の立案を行わない
  → IPPO は研究結果の解釈・論文執筆を行わない
  → IPPO は「Dataset の提供と品質保証」のみを行う

例外（IPPO 自身が研究主体になりうるケース）:
  → Founder が「IPPO の Research Dataset の分析結果」を学術論文として発表する場合
  → この場合は IPPO 自身が倫理審査を受ける必要がある
  → Wave4 以降に検討。現時点では実施しない。
```

### 3-B. IRB 要件の段階別整理

```
Phase 1〜2（Wave2 完了前）: IRB 不要
  → Dataset を外部に提供しない段階
  → 内部分析（Founder による品質確認）のみ → IRB 不要

Phase 3〜4（Wave2〜3 / 2028〜2030年）: 研究機関への Dataset 提供
  → 提供先（大学・研究機関）が自機関の倫理委員会（IRB 相当）の承認を取得する
  → IPPO は「IRB 承認証明の提出」を提供条件に含める（BBS-002 に明記済み）
  → IPPO 自身は IRB を取得しない（提供者の立場を維持する）

Phase 5〜6（Wave3〜4 / 2030〜2033年）: 製薬企業への提供
  → 製薬企業の R&D は「臨床研究法」の適用を受ける場合がある
  → 特定臨床研究に使用するデータとして IPPO の Dataset が使われる場合、
    臨床研究法の要件（CRB 承認等）が適用される可能性がある
  → この段階では法律専門家・CRO（Contract Research Organization）との
    協力体制を整える（Founder 一人では対応困難）
  → ただし BBS-001（Founder 哲学準拠）: CRO とのパートナーシップは
    「データ品質確認補助」に限定し、研究設計には関与させない

Phase 6〜7（Wave5〜 / 2033年〜）: 国際研究利用
  → DOI 付き Dataset の国際提供では、各国の倫理審査基準への対応が必要
  → IRB-equivalent（例: 欧州の Ethics Committee）の承認を条件とする
```

### 3-C. 同意取得（Consent）と研究利用の整合性

```
現在の Consent 設計（BD-002）で研究利用はカバーされているか:

  問題:
    Wave1 段階の Consent は「IPPO アプリの機能利用」を主目的として設計されている。
    「あなたの匿名化データが学術研究に利用される可能性がある」という
    Research Consent が明示的に含まれているかは不明。

  推奨対応:
    「Research Consent」を独立した Consent 項目として追加する。
    ユーザーが「研究利用に同意する / しない」を明示的に選択できる設計にする。

  Research Consent の設計方針:
    → デフォルト: オプトイン（明示的な同意がある場合のみ研究利用可）
    → 同意項目:「あなたの匿名化済みデータが、女性疾患の学術研究に
                  利用される可能性があります。同意しますか？」
    → 撤回: いつでも可能（撤回後の過去 Dataset への影響は別途定義）
    → 注意: Research Consent を撤回しても IPPO の機能は引き続き使える

  撤回後の扱い:
    → 撤回以降の新規 Record は Research Dataset の対象外にする
    → 撤回前の匿名化済み Research Dataset への遡及的削除は
      「k-anonymity の特性上困難」を理由に「不可」とする
      （この旨を同意画面で事前に説明する）
```

**決定 R-CR-01:** Research Consent を独立した Consent 項目として Wave2 Phase D 前に追加設計する（実装時期は Phase A〜B の間）。Research Consent なしのユーザーの Record は Research Dataset の対象外とする。

### 4-C. Consent 撤回の運用方針

```
撤回の種類と影響範囲:

  基本サービス利用同意の撤回（= アカウント削除）:
    → 新規 Record の保存停止
    → 個人を特定できるデータの削除 or 匿名化処理
    → 匿名化済みの Research Dataset への遡及影響なし（k-anonymity 特性）
    → consent_events の完全削除は不可（BD-002）
      → userId を別 ID に置換する「非個人化」を実施する

  Research Consent の撤回（サービスは継続利用可能）:
    → 撤回以降の Record は Research Dataset 対象外
    → 撤回前の匿名化済み Dataset への影響なし（事前説明済みであること）
    → 撤回記録を consent_events に追記する（Append-Only）

  AI 利用同意の撤回（Premium/Pro 継続の場合）:
    → Signal Insight / Pattern Discovery の提供停止
    → プランは継続（有料機能の一部が使えなくなる旨を事前説明）

Consent 証跡の保管:
  → consent_events テーブル（Supabase / Immutable / BD-002）
  → 項目: userId / consentType / version / action（GIVEN/WITHDRAWN）/ timestamp / ipAddress
  → 保管期間: 最低「法的請求があった場合に証明できる期間」= 10年推奨
```

## 5. 医師アドバイザー戦略

### 5-A. なぜ医師アドバイザーが必要か

```
理由 1: AI Safety の医学的根拠
  「Signal Insight の文言が医学的に正確か」を Founder 単独で判断することは
  医師免許のない者による医学的判断になりうる。
  医師アドバイザーの文言承認が「医学的正確性の証明」になる。

理由 2: SaMD 規制リスクの軽減
  「婦人科専門医が監修している」という事実は、
  薬事当局が IPPO の AI 機能を評価する際の重要な加点要素になる。

理由 3: Research Dataset の信頼性向上
  「医師が監修した Knowledge Graph / Dataset」は
  研究機関が利用する際の信頼性が飛躍的に上がる。

理由 4: 将来の Clinic B2B の入口
  医師アドバイザーが「自分のクリニックでも使いたい」と感じれば、
  B2B Clinic パイロットへの最初の入口になる。

理由 5: ユーザー信頼の向上
  「○○病院 婦人科医 ●● 先生が監修」は、
  Flo / Clue との差別化として最も効果的な一つである。
```

## 8. 海外展開 規制整理

### 8-A. 台湾（最初の展開）

```
適用規制: 個人資料保護法（個資法 / 2015年改正）

要点:
  ① 要配慮個人情報（病歴・医療記録）の収集には「本人明示同意」が必要
     → 日本の個人情報保護法と類似。現在の Consent 設計で対応可能。

  ② 国際転送:
     台湾の個人資料は「日本のサーバー（または Supabase 米国）」に移転される。
     台湾法: 国際転送は原則許可（一定条件あり）。
     対応: プライバシーポリシーへの明示 + Supabase のデータ保護方針の提示。

  ③ 病歴データの第三者提供:
     書面による同意が必要（口頭不可）。
     → 台湾展開時の Consent フローを「書面同意（電子書面）」に設計する。

  ④ 個人資料保護官制度:
     台湾では「個人資料保護長」の指定が義務化される動向がある（2023年改正動向）。
     → 台湾展開前に最新の法律動向を確認する。

難易度評価: ★★★☆☆（中程度 / 日本と類似するため比較的対応しやすい）

Founder の追加作業:
  → 台湾の法律専門家（スポット相談）: 5〜10 万円
  → 繁体字プライバシーポリシーの法的レビュー: 3〜5 万円
```

### 8-B. 韓国

```
適用規制: 個人情報保護法（PIPA / 2020年改正）

要点:
  ① 要配慮個人情報（건강정보 / 健康情報）の処理には「明示的同意」が必要。
     → 日本と類似。現在の Consent 設計で対応可能。

  ② 個人情報保護委員会（PIPC）への登録義務:
     韓国内で個人情報を処理する場合、一定規模以上は PIPC への登録が必要。
     → 韓国展開前に登録義務の有無を確認する。

  ③ 国外移転:
     韓国法は国外移転に厳しい規制がある。
     「標準個人情報保護契約（SCC）」の締結 or 本人同意が必要。
     → Supabase（米国）へのデータ転送が対象になる可能性がある。

  ④ データローカライゼーション:
     韓国では一部業種でデータの国内保存義務がある。
     ヘルスケアアプリへの適用有無を確認する。

  ⑤ 罰則:
     韓国の PIPA 違反の罰則は日本より厳しい（最大 3% の売上課徴金）。

難易度評価: ★★★★☆（やや難しい / 国外移転規制が特に注意が必要）

追加作業:
  → 韓国の法律専門家（スポット相談）: 10〜20 万円
  → SCC 締結 / 本人同意フローの設計
```

### 8-C. オーストラリア

```
適用規制: Privacy Act 1988 / Australian Privacy Principles（APPs）

要点:
  ① 健康情報（Health Information）は「センシティブ情報」として
     特別な取扱いが必要。月経・疾患データはすべて該当。
     → 収集には「明示的同意」が必要。

  ② 国外移転（Australian Privacy Principle 8）:
     国外にある受取人に個人情報を提供する場合、
     本人同意 or 同等の保護水準の確保が必要。
     Supabase（米国）への転送が対象になる。
     → プライバシーポリシーへの明示 + 本人同意で対応可能。

  ③ My Health Record との関係:
     オーストラリアには政府運営の医療記録システム（My Health Record）がある。
     IPPO は My Health Record とは独立したシステムであることを明示する。

  ④ TGA（医薬品・医療機器管理局）:
     AI 機能が SaMD に該当する場合、TGA の登録が必要になる可能性がある。
     → 日本での SaMD 相談（R-AI-02）の結果をオーストラリア TGA の
       ガイドラインと照合する。

  ⑤ ACCC（消費者競争委員会）:
     ヘルスケアアプリへの広告規制がある。IPPO は広告を使わないため低リスク。

難易度評価: ★★★☆☆（中程度 / 英語圏で情報入手しやすい）

追加作業:
  → オーストラリアの法律専門家（スポット相談）: 15〜25 万円
  → 英語版プライバシーポリシーの法的レビュー
```

### 8-D. 米国（将来 / 慎重）

```
適用規制: HIPAA / Dobbs 後の州法 / FDA SaMD 規制 / CCPA（カリフォルニア）

要点:
  ① HIPAA（医療情報秘密保護法）:
     IPPO は「Covered Entity」（医療機関・保険会社等）ではないため、
     HIPAA は直接適用されない可能性がある。
     ただし「Business Associate」として HIPAA 対象機関と連携する場合は適用。
     → HIPAA 適用の有無を米国弁護士に確認する。

  ② Dobbs 後の月経データ問題:
     複数の州で「月経追跡データが法執行機関に提供を強制される」リスクがある。
     → 「月経データを法執行機関に提供しない」ポリシーの制定
     → 「月経データを暗号化し、IPPO も復号できない設計」の検討
     → 米国展開は 2034年以降。その時点の法的状況を再評価する。

  ③ FDA SaMD 規制:
     米国の FDA SaMD 規制は日本の薬機法より範囲が広い。
     「Clinical Decision Support」ソフトウェアへの FDA 規制適用有無を確認。

  ④ CCPA（カリフォルニア消費者プライバシー法）:
     カリフォルニア居住者が含まれる場合に適用。
     Health Data への CCPA 規制（CPRA 改正後）の対応が必要。

難易度評価: ★★★★★（最難 / BGS-004 準拠で 2034年以降に先送り）

推奨: 米国展開の検討は 2033年以降。その時点で専門弁護士との戦略会議を別途開催。
```

| **BD-046** | Research Dataset の外部提供前に、提供先機関の倫理委員会（IRB 相当）の承認証明書を IPPO が受領することを必須とする。証明書未受領での提供を絶対禁止する |
| **BD-047** | IPPO のプライバシーポリシーは年 1 回以上、弁護士または法律専門家によるレビューを受けること。レビューなしで 12ヶ月以上経過したプライバシーポリシーの運用を禁止する |
| **BD-048** | AI 出力の禁止ワードリストは医師アドバイザーが半年ごとにレビューし、Founder が承認すること。禁止ワードリストを 12ヶ月以上更新しない状態での AI 機能の新規公開を禁止する |
| **BD-049** | Research Consent（研究利用同意）を持たないユーザーの Record を Research Dataset に含めることを絶対禁止する。Research Consent はオプトイン方式とし、デフォルトは非同意とする |
| **BD-050** | IPPO は「医療行為の代替」であることを示唆する表現を、いかなる媒体（アプリ内 / LP / SNS / 広告等）でも使用してはならない。使用する場合は医師アドバイザーの事前承認を必須とする |
| **BD-051** | Wave2 Phase D（PR-057: Signal Insight Service）の着手前に、薬事専門弁護士または薬事コンサルによる「SaMD 非該当の書面見解」を取得することを Founder が宣言的に必須とする。取得なしの Phase D 着手を禁止する |
| **BD-052** | 海外展開（台湾・韓国・オーストラリア・EU・米国）は、対象国の医療データ規制専門家による書面確認を取得した後にのみ開始できる。確認なしの海外ストア公開を禁止する |

## 13. Final Decision（GO / CONDITIONAL GO / NO-GO）

### Council 最終判定

```
CONDITIONAL GO

IPPOの規制・医療・倫理の基本設計は正しい。
BD-001〜BD-043 の設計は国際水準の医療データガバナンスに沿っている。

しかし「設計が正しいこと」と「法的に安全であること」は別である。

以下 5 条件を満たすことで「完全な GO」になる:
```

### 条件一覧

| # | 条件 | 期限 | 担当 |
|---|---|---|---|
| C-1 | プライバシーポリシーの弁護士レビュー完了 + 要配慮個人情報対応 | Wave2 Phase A 前 | Founder + 弁護士 |
| C-2 | 医師アドバイザー 1 名の招聘 | Wave2 Phase D 前 | Founder |
| C-3 | SaMD 非該当の書面見解取得（BD-051）| Wave2 Phase D 前 | Founder + 薬事専門家 |
| C-4 | Research Consent の Consent フローへの追加（BD-049）| Wave2 Phase B 前 | Founder（実装）|
| C-5 | Research Dataset 提供契約書雛形の作成 | Wave2 Phase F 前 | Founder + 弁護士 |

### Council 所見

```
IPPO の設計哲学は「患者の信頼を守ること」を最優先にしている。

BD-002（Consent Immutability）
BD-030（個人特定 ZERO TOLERANCE）
BD-031（AI 診断禁止）

これらは「法的義務だから守る」のではなく
「それが正しいから守る」という設計になっている。

この哲学こそが IPPO の最大の強みであり、
同時に「規制と戦わなくていい」最大の理由である。

法律は最低ラインを定める。
IPPO はその最低ラインを遥かに上回る設計をすでに持っている。

Founder はこれ以上の規制対応を「恐怖から」行う必要はない。
「信頼の証明のため」に、本文書の 5 条件を順序よく実行すればよい。

10年後、IPPO が「最も信頼できる女性疾患データプラットフォーム」になる根拠は、
技術にも、データ量にも、そして「最初から正しく作ってきた証拠」にもある。

Council 全員一致で Conditional GO を推奨する。
```
