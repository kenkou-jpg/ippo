## 2. テーマ別ディスカッション

### テーマ1: IPPOは何のアプリ？一言で。

- **Prototype Designer**: 「自分の体で実験して、パターンを発見するための実験ノート」。診断でも治療でもない。あくまで個人の記録と観察。
- **現行IPPO Architect**: 技術的には3層ある。①症状記録ツール、②自己実験フレームワーク（Experiment Domain）、③疾患クラスタ研究基盤（`disease-cluster-statistics-service`, `similarity-engine-v2`, `pattern-discovery-service`等、`src/domains/`配下に20以上のドメインサービスが存在）。この③はPrototypeには対応物が無い、現行IPPO固有の資産。
- **女性疾患ユーザー**: 実際に`ippo-rebuild`のオンボーディングを見ると「PMS/PMDD/PCOS/子宮内膜症/卵巣嚢腫/特にない」という疾患選択が最初に出てくる（今回のセッションで実機確認済み）。つまりPrototype自体も「誰でも使える汎用実験ノート」ではなく、婦人科系の悩みを持つ人を強く意識した入り口になっている。ここは以前のCouncil記録（「疾患特化コンテンツはPrototypeの欠落」）と食い違う可能性があり、**Prototypeの現状を再確認する価値がある**（本Councilでは深掘りせず、事実として記録するに留める）。

**論点**: 「汎用実験ノート」と「婦人科系ユーザー向けツール」の間で、Home画面のコピーやオンボーディングの重心が揺れている。どちらを一次アイデンティティにするかは製品の根幹に関わる。

### テーマ2: ユーザーは毎日何を開きに来る？

- **Habit Designer**: Prototype Heroが提示する4つの「今日」——今日の記録／今日の発見／今日の実験／今日の達成——のうち、新規ユーザーには**そのほぼ全てが空状態**になる。実機確認済み: 「🌱まだ実験はありません」「今日はまだ記録していません」「まだ十分なデータがありません」。3つの空状態が同時に出るHome画面は、初日の開く理由として弱い。
- **Product Designer**: 空状態自体のコピーは丁寧（「記録を続けると実験を始められます」等）で、威圧感はない。ただし「何をすれば空状態を脱せるか」への導線は記録CTA一本のみで、視覚的な優先順位付けが弱い。
- 既存監査（`First 30min & Emotional Journey Audit`、本Councilの外部で既に実施済み）が「Day0初回起動状態が存在しない」を既に指摘している。**本Councilはこの既存の指摘を追認する**（新規発見ではない）。

### テーマ3: 初回登録後、何を体験する？

- Prototype: 疾患選択（任意）→「まずは3日間、なんとなく気になることを記録してみましょう」という具体的な最初のミッションが明示される。
- 現行Runtime（Home Rebuild後）: 同様に「気になることを3日間、記録してみましょう」という「今日の目的」テキストは既存要素として残っている（`hn-personalize`等）。ここはPrototypeとの体験ギャップが比較的小さい。
- **Habit Designer**: 「3日間」という具体的な数値目標を提示している点は行動科学的に妥当（次の実験候補が出る条件`MIN_RECORDS=3`と一致しており、有言実行になっている）。これは良い一貫性。

### テーマ4: 30日後、何が変わる？

- Before→After結果カード・Milestoneバナーは実装済みで、「記録が結果に変わる」という体験の骨格は存在する。
- **SaaS PM**: ただし到達までの導線が受動的——ユーザーが自発的に実験を完了させない限り何も起きない。14日〜30日という期間、能動的にユーザーを引き戻す仕組み（通知・リマインド）が現状のRuntime実装範囲内では確認できていない（`temp-alert.js`等の既存モジュールはあるが、今回の3PRのスコープ外であり中身は未検証）。**ここは断定を避け、要確認事項として記録する**。

### テーマ5: Premium 月580円 本当に払う？

- **女性疾患ユーザー**: Premiumの訴求機能は「Insights全履歴の閲覧」「周期×体調の長期トレンド」「パターンカレンダー全期間表示」——いずれも**量（もっと見える）の拡張**であり、**質（新しい気づき）の追加**ではない。無料でも「今週のハイライト」「直近28日のパターンカレンダー」は見える設計になっているため、Premiumの便益を実感するには数ヶ月分の記録データが既に自分の手元にある必要がある。
- **SaaS PM（重要な指摘）**: これは構造的に**既存ユーザーの継続課金には効くが、新規ユーザーの初回購入トリガーにはなりにくい**設計。新規ユーザーは「全履歴」を欲しがるほどのデータをまだ持っていない。つまりPremiumは「Retention Monetization」であって「Acquisition Monetization」ではない。この非対称性をFounderが意図しているか確認が必要。
- **Habit Designer**: 580円という価格自体は衝動購入の範囲内で、価格が壁になっている可能性は低い。壁になっているのは「今すぐ払う理由の提示」の弱さ。

### テーマ6: Pro 必要？今必要？β後？

- 全員一致: **今は不要**。Founder決定（β後）を支持する。
- **Stripe担当**: 現行のStripe/Edge Function実装は`monthly`/`annual`の2キーのみで単一商品しか扱えない（`supabase/functions/stripe-checkout/index.ts`確認済み）。Pro相当の別商品を売るには、Stripe Dashboardでの新Price作成とEdge Functionの`PLAN_PRICE_MAP`拡張が前提になる。技術的にもβ後が妥当。
- **SaaS PM（コピーの正確性への指摘）**: Proの訴求文言に「AIによる次の実験提案」とあるが、実装済みの`ExperimentNudgeService`はルールベース判定（直近記録の平均痛みレベルが閾値以上、または同一食品・症状が3回以上出現、等の条件分岐）であり、LLM/AIモデルではない。`AI_EXECUTION.md`自体が「AI/LLM/医療判断の実装は禁止」と明記している。将来的に実際のAI提案機能を作る計画が無いなら、「AIによる」という文言は誇大表現になるリスクがある。**Pro実装時に是正すべき事項として記録**。

### テーマ7: Prototype 現行IPPO どちらを正とする？

- **現行IPPO Architect**: 直近3PR（Home/Experiment/Me Rebuild）は一貫して「Prototype構造を正、実データは既存Domain/Applicationへ接続」という方針で進め、**Domain層の変更は一度も必要にならなかった**。これは現行IPPOの土台（Domain/Application層）が健全であることの実証結果であり、ギャップは常にUI/Runtime層だけにあった、という仮説を裏付けている。
- 結論: 「どちらを正とするか」という問い自体は既にこのセッション内で実務的に決着している——**Prototype＝UI構造の正、現行IPPO＝Domain/データの正**というハイブリッドは機能している。今後もこの方針を継続すべき。

### テーマ8: 5画面をユーザー目線で採点（100点満点、AIによる構造・コンテンツ監査に基づく推定値。実ユーザーテストではない）

| 画面 | 推定スコア | 根拠 |
|---|---|---|
| Home | 75 | 骨格は強い（Ring/Streak/Milestone/Result/Next全実装）が、新規ユーザーは空状態が3つ重なる。既存セクションの並び順がPrototype完全準拠ではない（95%構造一致） |
| Experiment | 80 | 進行中→完了/中止→おすすめの実験という一連のループが揃った数少ない画面。Prototype一致率100%達成 |
| Insights | 70 | 構造は100%一致だが、価値実感が「記録の蓄積後」に偏る（テーマ5と同じ非対称性） |
| Me | 50 | Planカードは追加されたが、設定リスト5行中3行（通知設定・データのエクスポート・アカウント）と「気になることを変更する」がクリック不可のまま。未完成な設定画面という印象が強い |

### テーマ9: Prototypeより現行の方が良いものは？

- **疾患クラスタ研究基盤**（Similarity Engine, Cohort Builder, Pattern Discovery等）: Prototypeには対応する仕組みが無い、現行IPPO固有の深い資産。ただし現状のRuntime UIからはほぼ見えていない（活用されていない）。
- **Consent/同意管理の実装**（`consent-service.js`、2026-07-18実装）: Prototypeは静的な安心コピーのみで、実際の同意取得・撤回フローを持たない。
- **Experimentの完了/中止ライフサイクル**: Prototypeのデモではボタンが機能しないが、現行RuntimeはApplication Facade経由で実際に動く。

### テーマ10: 全部捨てるなら何だけ残す？

- **Habit Designer + Architect 共通見解**: 「記録する→実験を組む→結果を見る」という中核ループ（Record → Experiment lifecycle → Result）が残れば、Founderの一文（「信頼できる形で積み上げられる実験ノート」）は成立する。Insightsの可視化、Milestoneの演出、疾患パーソナライズ、Billingは、この中核ループの上に乗る"体験の厚み"であり、中核ではない。

## 3. 最終成果物

### 3-1. IPPO PRODUCT THESIS v2

> **IPPOは、自分の体で行った小さな実験（食事・睡眠・行動の変化）が、実際に症状にどう影響したかを、
> 記録の積み重ねだけで確認できる自己実験ノートである。診断・治療の代わりにはならないが、
> 「なんとなく」で終わっていた体調の変化を、自分自身の記録という一次データで裏付ける。**

Founder原案からの変更点: 「信頼できる形で積み上げられる」の"信頼"を、「記録の積み重ねだけで確認できる」という
具体的な機能（Before→After結果カード）に紐付けた。抽象的な信頼ではなく、機能で担保する。

### 3-2. Premium価値（再定義提案）

現状の「もっと見える」訴求だけでなく、**新規ユーザーが最初の実験を完了した直後**に
「これをもっと詳しく見たいなら」という文脈でPremiumを提示する動線を推奨する
（現状のPremium訴求はMe/Billing画面での静的提示のみで、Result Card表示のタイミングとは連動していない）。
これは実装判断ではなく、次PR以降の検討事項として記録する。

### 3-3. Pro価値（再定義提案）

「AIによる次の実験提案」の文言は、実装がルールベースである間は「あなたの記録パターンから次の実験を提案」等、
技術的に正確な表現へ修正することを推奨する。Proの中核価値は「カスタム実験の作成」「複数実験の同時進行」に
絞り、AI表現は実際にLLM/MLベースの提案機能を作る段階まで保留すべき。

### 3-4. MVP（β時点での必須範囲）

```
Home:       Hero Ring / Streak / Record CTA / Insight card（既存）
Experiment: 進行中カード / ライブラリ / 完了・中止UI / おすすめの実験
Insights:   今週のハイライト / Pattern Calendar（28日） / Premium Overlay
Me:         プライバシーカード / Consent UI / Planカード要約 / 現在のプラン表示
Billing:    Premium Checkout接続（Proは非接続のまま「準備中」表示）
```

### 3-5. βリリース条件

```
□ PR-HOME-REBUILD-01 / PR-EXPERIMENT-REBUILD-01 / PR-ME-REBUILD-01のFounder Browser Verification（Home/Experiment/Meは完了済み、Meは未確認）
□ Billing Premium Checkout接続 + Founder Browser Verification
□ Feature Flag 5画面のデフォルトON切替タイミングの決定（現状すべて既定OFF）
□ Me設定リスト（通知設定/データのエクスポート/アカウント/気になることを変更する）を「実装する」か「本PRでは非表示にする」かの決定
   → クリックできないダミー行を残したままのβ公開は避けるべき（テーマ8のMe画面採点の主因）
```

### 3-6. 削除機能（候補）

- Me画面の非機能設定行（通知設定/データのエクスポート/アカウント）: 実装するか、実装できるまでβでは非表示にするか、いずれかを選ぶべき。「見えるが押せない」状態が最も体験を損なう。

### 3-7. 追加機能（候補、優先度順）

1. Home Day-0（新規ユーザー）向けの導線強化: 3つの空状態が同時に出る問題への対処（優先度: 高）
2. Result Card表示タイミングに連動したPremium訴求（テーマ5/3-2）
3. Me設定リストのクリック機能復活（既存の別ギャップ、繰り返し記録されている）
