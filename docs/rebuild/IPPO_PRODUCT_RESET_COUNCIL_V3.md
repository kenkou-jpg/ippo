## 0. Founder決定事項（議論対象外、前提として固定）

```
① IPPOはシリーズ展開する。第一弾は「女性疾患特化版」
② 共通コンセプト: 目標設定 → 日々の記録 → AIが分析 → 数値化・可視化 → 次に試すことを提案
③ Homeがアプリの中心。Homeだけで「今日の目標/記録/変化/提案」が完結する
④ Experimentはユーザーに見せない内部ロジックへ
⑤ AIは診断・治療をしない。読む・数値化する・傾向を見つける・改善率を出す・提案するのみ
⑥ 女性疾患版の対象: PMS/PMDD/子宮内膜症/PCOS/卵巣嚢腫/生理痛/月経不順
```

## 2. ① Product Thesis

**20字**: 「体の変化に気づける、女性の実験ノート」

**50字**: 「PMSや生理痛など女性特有の不調を、毎日の記録とAI分析で可視化し、次に試すことまで導く自己観察アプリ。」

**200字**: 「IPPOは、PMS・PMDD・子宮内膜症・PCOS・生理痛・月経不順など女性特有の不調を抱える人のための自己観察アプリです。毎日の簡単な記録をAIが読み取り、数値化・可視化することで、『なんとなく辛い』を『いつ・何が・どう変化したか』という自分自身のデータに変えます。診断や治療の代わりにはなりません。AIは記録を分析し、次に試せる小さな行動を提案するだけです。目的は、あなたが自分の体について、これまでより少しだけ確信を持てるようになることです。」

**Council合意**: 3つの粒度に共通するのは「気づき（記録→変化の可視化）」であって「実験」という言葉ではない。Founder決定④の通り、ユーザー向け言語から「実験」は原則排除する。

## 3. ② 本当の価値 — ユーザーは何にお金を払うのか

- **女性疾患ユーザー**: 女性疾患・生理関連の不調は「病院に行っても『よくあること』で流される」「セルフケア記事は一般論ばかりで自分に当てはまるか分からない」という体験が多い。欲しいのは診断ではなく、**「自分の場合はこうだった」という一次データに基づく確信**。
- **Product Manager**: Founder提示の5候補（記録/安心感/改善実感/AI分析/未来への希望）のうち、課金トリガーになるのは「安心感」でも「AI分析」そのものでもない。**「改善実感」への最短距離を提供すること**が価値の核。記録やAI分析は手段であって、ユーザーが金を払うのは「変化が見えた」という結果に対して。
- **Habit Designer**: 初期（記録が貯まる前）は「安心感」（記録すること自体が不安の軽減になる、これは無料でも成立する体験）。中期（1〜2周期分のデータが貯まった後）に「改善実感」へ価値がシフトする。**課金ポイントは中期に置くべき**——早すぎると何もまだ見せられず、遅すぎると習慣が定着せず離脱する。

**言語化**: 「あなたの記録が、あなた専用の“これは効いた”を教えてくれるから。」

## 4. ③ Home — 何を残し、何を削るか

**UX Designer**: 現行Runtime（改善版）のHomeには実測で13前後のセクション（ヘッダー/挨拶/デイリーノート/Hero Ring/Milestone/ステータス/パーソナライズ/Optional/Recovery/Reflections/Insights/医療サマリー/Result/Next-experiment/Record）が存在する。ゼロベースでは**4ブロックまで削る**。

```
Home（ゼロベース仕様）
┌─────────────────────────┐
│ 1. 今日の目標              │  例:「今週の目標: 生理痛を軽くする」1行
├─────────────────────────┤
│ 2. 今日の記録（未実施なら最優先表示） │  1タップ、10秒以内
├─────────────────────────┤
│ 3. 今日の変化               │  1つの数値/グラフのみ。無ければ「まだデータが足りません」の1行
├─────────────────────────┤
│ 4. 今日の提案               │  1枚のカードのみ。無ければ非表示（複数出さない）
└─────────────────────────┘
```

**削除**: ストリークドット・ヘッダーの挨拶文・複数の「はじめに」的コピー・疾患パーソナライズの独立カード・Recovery Journey・Reflections・医療サマリーの独立表示——これらは**「今日の変化」1ブロックに統合するか、Home外（詳細画面）へ移す**。

**Habit Designer**: 4ブロックのうち、ユーザーが最初に目を落とすのは「2. 今日の記録」であるべき。目標や変化より先に、今すぐできる行動を最上部に置く設計（現行Prototype/Runtime双方の「まず記録」という思想は正しい、位置の優先順位だけ見直す）。

## 5. ④ 目標設定

**Product Manager + 女性疾患ユーザー**: 自由入力は分析可能性を壊す（AIが数値化できない）ため主入力にしない。ただし「何も当てはまらない」ユーザーを弾かないよう、**選択式＋補助的な一言メモ（任意・分析対象外）**の二層構成にする。

```
主要目標（単一選択、後から変更可）:
  □ 生理痛を軽くしたい
  □ PMS（生理前の不調）を改善したい
  □ 生理周期を整えたい
  □ 疲れにくくなりたい
  □ 気分の浮き沈みを減らしたい
  □ まだよく分からない（記録しながら決める）

補助メモ（任意、AI分析には使わず表示のみ）:
  自由入力欄「具体的に困っていることがあれば」
```

「まだよく分からない」を明示的な選択肢にすることが重要（Founder決定⑥の対象者は診断名を持たない人も多いため、選択を強制しない）。

## 6. ⑤ 毎日の記録 — 必要最低限

**Habit Designer**: 「多すぎて続かない」を避けるため、**目標に連動した1つの主指標＋任意のコンテキストタグのみ**。

```
必須（10秒以内）:
  - 今日の症状の強さ（1〜5のスケール、目標に応じて文言変化。例: 生理痛が目標なら「今日の痛み」）

任意（ワンタップ、スキップ可）:
  - 気分（絵文字5段階）
  - 今日あったこと（食事/睡眠/ストレス/運動から複数選択、チップ形式）

完全に削除:
  - 詳細な症状リスト全項目の毎回入力
  - 体温等の毎回手入力（周期トラッキングに必要な項目はあるが、Founder決定の対象がPMS/PCOS等広範なため、必須にはしない）
```

**女性疾患ユーザー**: 生理周期に関する記録（開始日）だけは別枠で月1回程度の頻度でよく、毎日の記録に含めない。周期記録と症状記録を同じ画面で毎日聞かれるのは負担。

## 7. ⑥ AI分析 — 何を自動で見るか

優先順位順（CTO/Architect: 実装容易性、Product Manager: ユーザー価値の両面で評価）:

1. **症状スコアの推移**（記録した強さの単純な時系列、最も実装が軽い）
2. **周期との関係**（生理周期の中で症状がいつ強まるか。女性疾患版の最大の差別化要素）
3. **継続率・記録の一貫性**（分析というよりモチベーション表示に近いが、「見える化」の入口として機能）
4. **改善率**（目標設定時の初期値と直近平均の比較。「効いた」感を最も直接的に生む）
5. **食事・睡眠との関係**（データが十分に貯まった場合のみ。優先度は最も低い——相関の質が弱くなりがちなため）

**CTO/Architect注記**: ①③は既存の`experiment-progress.js`相当のロジックで対応可能。②はドメインとして新規（周期データと症状データの時系列相関）。⑤は既存`ExperimentNudgeService`のパターン検出ロジックの延長線上。

## 8. ⑦ AI提案 — 何を提案し、何を提案しないか

**提案すること**:
- 今日やること（1つだけ。例:「今日は白湯を飲んでみましょう」）
- 次に試すこと（週〜月単位、内部的には「実験」だが表現しない。例:「来週は睡眠時間を意識してみましょう」）
- 記録から見えた傾向への気づき（例:「生理開始3日前に痛みの記録が増える傾向があります」）
- 同じ状態が続く場合の注意喚起（医療者への相談を促す、診断はしない）

**提案しないこと（明示的な禁止事項）**:
- 病名・診断名の推測（「あなたはPCOSかもしれません」等）
- 薬・サプリの用量や服薬指示
- 治療の開始・中止の助言
- 「治る」「効果がある」等の断定的改善表現（既存の禁止語リストを継続適用）
- 医療者の判断を上書きする表現

これは現行`AI_EXECUTION.md`の「AI/LLM/医療判断の実装は禁止」および既存の非断定表現ルールと完全に整合する。ゼロベース設計でもこの制約は変更しない。

## 9. ⑧ Premium — 580円払う理由

**Product Manager**: v2 Councilで指摘した「量（もっと見える）」ではなく「質（新しい気づき）」を売る。

**一文**: 「生理周期と症状の関係を、AIが毎月自動で教えてくれるから。」

無料版は「症状スコアの推移」「継続率」まで。有料版は「周期との関係」「改善率」「次に試すことの提案」——**AI分析の“相関”レイヤーを課金境界にする**。これなら新規ユーザーでも1周期分（約1ヶ月）のデータが貯まった時点で価値を実感でき、v2で指摘した「新規ユーザーに何も見せられない」問題を解消できる。

## 10. ⑨ シリーズ展開 — 共通化と差し替え

| 共通化する | 差し替える |
|---|---|
| 目標設定→記録→AI分析→可視化→提案のループ構造 | 目標の選択肢リスト（症状体系） |
| 記録データモデル（症状強度+気分+タグの基本形） | 分析ロジックの相関対象（女性疾患=周期、断食=空腹窓、睡眠=睡眠段階、腸活=食事） |
| Habit/ストリーク機構 | オンボーディングのコピー・ビジュアルアイデンティティ |
| Consent/プライバシー基盤 | 免責文言の疾患領域別調整 |
| 認証・課金基盤（Stripe連携） | AI提案の文言テンプレート |
| Home 4ブロック構造そのもの | 「今日の記録」の主指標定義 |

**CTO/Architect**: 現行コードベースの`Record`ドメイン・`Experiment`ドメイン（内部的に維持、UI用語からは排除）・`Consent`・`Premium`基盤はそのまま横展開可能な設計になっている。3PR（Home/Experiment/Me Rebuild）を通じてDomain層の変更が一度も必要なかった事実が、これを裏付けている。**シリーズ展開に必要なのは新しいDomainではなく、「vertical設定」という差し替え可能な構成レイヤーの新設**。

## 13. ⑫ 作り直すべきか（A/B/C/D）

**Council結論: C（共通プラットフォームとして再構築する）**

理由:
- **A（現行IPPOを改善する）を採らない理由**: 現行Homeは13前後のセクションを持つ「積み増し型」設計であり、Founder決定③（Home 1画面完結・4ブロック）へ改善で到達するには実質的に大部分を作り直すことになる。改善の名目でゼロベース設計と同等のコストがかかる。
- **B（UIだけ全面リニューアル）を採らない理由**: 「実験を裏側に隠す」「目標設定を起点にする」はUIだけの変更では済まない。ユーザーへ提示する情報構造・導線そのものの再設計が必要で、UI層だけの変更では中途半端になる。
- **D（完全新規開発）を採らない理由**: Record/Experiment/Consent/Premiumの各Domain層、およびStripe決済基盤は、3PRの実績を通じて健全性が実証済み。ゼロから作り直すのは、既に動いている資産を捨てる過剰なコスト。
- **Cを推す理由**: 「Domain/決済/Consent基盤は流用」「UI構造・情報設計・vertical設定レイヤーは新規」という切り分けが最も合理的。かつFounder決定①（シリーズ展開）を見据えると、最初から「複数アプリが乗る共通プラットフォーム」として設計し直すこと自体がβの一部になる。

## 14. ⑬ マネタイズ戦略 — 「最初から300円」仮説の評価

### ① 有料化モデルの評価

| 選択肢 | メリット | デメリット |
|---|---|---|
| A. 最初から300円で買い切り販売 | 決済判断の摩擦が最小。サブスク疲れへの反発を避けられる。一人運営に対する運用負荷が最も軽い | 単発収益しか生まない。本製品は「周期相関」のように**継続的にデータが増えるほど価値が増す**設計のため、買い切りだと2ヶ月目以降の分析価値をマネタイズできない |
| B. 無料＋300円アップグレード | 新規ユーザーの導入障壁がゼロ。価値を体験してから払う設計にできる | アップグレードのタイミング設計を誤ると「何に対して払っているか」が不明瞭になる（v2で指摘した既存Premiumと同じ罠に陥る危険） |
| C. サブスク | 継続的な分析価値の提供と収益が一致する。将来のシリーズ展開時にも収益基盤として安定 | 「最初から300円」というFounderの仮説そのものと矛盾する。心理的ハードルもAより高い |
| D. その他（ハイブリッド） | 下記④で具体案を提示 | 設計・運用の複雑性が増す（一人運営には要注意） |

### ② 女性疾患市場で300円は適切か

- 国際比較: Flo Premium・Clue Plus は月額$9.99前後（約1,500円）。国内の同カテゴリ（ルナルナ Premium等）は月380〜480円が相場。300円はこれらの**月額**より安いが、**買い切り**として見ればJP App Store文化（ユーティリティアプリの買い切り相場300〜600円）に近い、自然な価格帯。
- 心理的ハードル: 極めて低い（「コーヒー1杯未満」）。参入障壁としては優秀。
- リスク: 女性疾患は当事者にとって切実なテーマであり、価格が安すぎることが「本気度・信頼性の低さ」のシグナルとして逆に響くリスクがある（Customer Success視点: 「安かろう悪かろう」という第一印象は、特に医療関連アプリでは離脱理由になりやすい）。

### ③ 300円なら当然あるべき最低限の体験

- 実際に「周期と症状の関係」という、その人固有のインサイトが最低1つは出ること（チャートを見せるだけでは不十分）
- 広告・追加課金の煩わしい訴求が一切ないこと
- 記録データのエクスポートができること（所有権の保証）
- 支払った直後に「何が変わったか」が体感できること（支払い後に空っぽの画面が出るのが最悪の体験）

### ④ 無料版は必要か

**必要**。本製品はAIが意味のある分析を返すために最低でも1周期分（約1ヶ月）の記録データを必要とする。データが無い状態でいきなり課金を求めても、Product Manager指摘の「新規ユーザーへの弱いアクイジション」問題を再現するだけ。**無料範囲＝記録＋症状スコアの推移＋継続率**（データが無くても即座に成立する体験）、**有料範囲＝周期相関＋改善率＋AI提案**（データが貯まって初めて意味を持つ体験）と明確に線引きする。

### ⑤ 将来のシリーズ展開での価格方針

課金の**仕組み**（無料の記録ループ＋有料のAI相関・提案）は全シリーズ共通にする（ユーザーが「IPPOシリーズはどれも同じ考え方」と学習でき、乗り換えコストが下がる）。**価格そのもの**はvertical毎に市場・データ濃度に応じて可変（女性疾患は感情的切実さが高く300〜500円帯、断食/睡眠等はより競合が多く価格競争が働きやすいため別途検討）。将来的な複数アプリ横断バンドル割引は、β後の検討課題とする。

### ⑥ Council最終判断

**結論: B（無料＋300円買い切りアップグレード）を暫定採用。ただし恒久的な単一モデルとは位置づけず、段階移行を前提にする。**

理由:
1. 一人運営・保守性を重視するSaaS Founderの立場から、サブスク特有の運用負荷（解約導線・支払い失敗時のリトライ・churn分析）を持たないBが、立ち上げ期には最も現実的。
2. Founder自身の仮説（300円）を尊重しつつ、「無料で記録ループを体験→周期相関が見える頃に300円」という設計にすることで、④で指摘した「データが無いのに課金を迫る」矛盾を回避できる。
3. ただし、**300円買い切りは本製品の「継続的に価値が増える」性質と本質的に相性が悪い**（①の指摘）。将来的には、300円買い切りを「Premium」の恒久的な入口価格として維持しつつ、複数目標の同時追跡・シリーズ全アプリ横断分析等を「Pro」として月額化する——**現行コードに既にある`FREE/Premium/Pro`の3層コード形状（`getTierLevel()`）は、この将来設計とそのまま整合する**。ゼロベース設計であっても、この一点だけは現行資産の先見性を評価し、引き継ぐ価値がある。
